# 游戏拆解案

把一个游戏拆成一份**经得起追问的专业拆解案**。**适用于任何品类**——动作、射击、RPG、开放世界、关卡制、卡牌、策略、模拟经营、竞技、解谜、免费手游。

产物是一份 markdown 文本，落在哪分两种模式（见「产物落在哪」）：独立仓库里它是 `README.md`
（GitHub 首页直接渲染），索引仓库里它是 `<游戏>/拆解案.md`。**本 skill 不碰 git**，上传是用户的事。

## 三条地基

1. **框架是骨。** 正文按六个设计域组织，不按用户的印象组织。框架规定要拆什么。
2. **内容从追问来。** 用户手里有游戏——数值、系统规则、关卡结构只有他能提供。
   访谈负责把"那关打不过"翻译成"该关敌人的有效血量 vs 玩家在该节点的期望输出"。
3. **事实是地板，判断是天花板。** 「用户没有观点」只豁免判断段，**不豁免事实段**。硬性域的事实段为空 = 没拆完。

## 六个域（通用）

| 域 | 必答 | 必产 |
|---|---|---|
| 一 · 核心循环与节奏 | 三层循环（单次操作 / 单局或单段 / 长线）、重心在哪层、时间轴、多久一次**有意义的决策**（不是操作） | 表 1 + 循环图 |
| 二 · 内容结构与关卡 | 关卡/地图/模式/阶段的划分与配比、硬门槛与保底、路径分支与**绕行成本**、崩盘点落在哪 | 表 1 + 结构图 |
| 三 · 数值与经济 | 结算结构（加算/乘算）、单位数值、成长曲线与压力曲线、两者比值、资源产出与定价、难度修饰、阈值与溢出 | 表 2-5 |
| 四 · 系统与内容池 | 逐系统走：目标→规则→输入输出→反馈→失败惩罚→边界漏洞。内容池（掉落池/技能池/关卡池…）、解锁与元进度、商业化（若适用） | 表 6-8 |
| 五 · 玩法机制 | 核心机制的经济：单次行动的收益与成本、可操作空间、信息透明度、上限与代价 | 表 9-10 |
| 六 · 反馈与表现（可选） | 一次交互的反馈层级、信息层级、手感与可读性、教学与引导 | 截图 |

**只有域六**允许"用户无观点就整域折叠"。其余五个域不豁免。

## 先定品类，再拆

同一套域，在不同品类里的内容不同。开拆前先认领一行，域二与域五照它替换：

| 品类 | 域二看什么 | 数值单位 | 内容池 | 机制经济（域五） |
|---|---|---|---|---|
| 动作 / 射击 | 关卡节奏、遭遇战布局、检查点 | DPS、TTK、命中与暴击期望 | 武器 / 技能池 | 单次交火的输出与生存成本 |
| 平台 / 关卡制 | 关卡与教学曲线、难度坡 | 移动速度、容错窗口 | 关卡池、机制池 | 操作精度与容错帧 |
| RPG / 开放世界 | 区域与任务结构、引导与自由度 | 属性、等级曲线、装备强度 | 装备 / 任务 / 敌人池 | 资源回路（血/蓝/药/金币） |
| 卡牌 / 回合制 roguelike | 层与节点配比、路线成本 | 有效血量、每回合输出 | 卡池、事件池 | 能量与费效比 |
| 策略 / 模拟经营 | 关卡或剧本结构、阶段目标 | 产出与消耗速率、平衡比 | 单位 / 科技 / 建筑池 | 决策的收益与延迟 |
| 竞技 / 多人 | 地图与模式结构、匹配机制 | 平衡数值、胜率 | 英雄 / 装备池 | 信息与反应窗口 |
| 解谜 / 休闲 | 关卡与难度序列 | 步数 / 时间 / 容错 | 关卡池、机制池 | 信息充分性 |
| 免费手游 | 引导与留存节点、卡点设计 | 体力与钻石的产出/消耗 | 卡池与概率 | 付费与玩法的挂钩 |

（示例字段，不是清单；不适用的格子跳过。）

## 每个域写三段

- **事实** — 数值表 / 规则 / 配比，一条一行，逐项标来源。**空着就是没拆。**
- **拆解** — 现象 → 机制 → 设计意图 → 代价与收益。机制必须落到数值或规则上：
  ❌"那关太难" ✅"该关敌人有效血量 X、玩家期望输出 Y，需要 N 回合（或 N 秒），超过这个数就没有容错空间"。
- **判断** — 一句**可被反驳的话** + 内部基准 + 外部对标 + 边界与证伪条件。想不清就写「本域无判断，待观察 X」。

**防退回说明书**：每域必须以判断收尾；空域显式留白，禁为凑齐而灌水。

## 文档骨架

产品卡片（平台/品类/上线/体量/样本量）· 核心发现索引（3-5 条跨域判断，**每条注明出自哪个域**）
→ 域一…域六 → 它付出的代价 → 如果我来迭代 → 附录 A 系统依赖（mermaid）· B 数值细节与交付物表 · C 曲线与图 · D 数据来源与可信度 · E 术语表。附录全部 `<details>` 折叠，结论前置。

**别的形状也行。** 交付物未必是六域拆解。若材料是"我的经历"而不是"游戏的系统"，用**旅程与留存复盘**：
案例卡片 → 核心发现 → 逐节点写三段 → 把它当作留存案例读 → 局限 → 附录。
（额外要求：自述与行为证据分开标注；必须给一条前瞻性可证伪预测；回溯偏差单列。）
若是比较两作，用**机制对照**：选定机制 → 各作三段 → 同口径对照表 → 落到具体数值的取舍点。

**换形状不换规矩。** 无论用哪种形状，三段法、来源三档、可证伪、算式与分母、禁用词、拦停、自检——一条不改。

## 交付物表（附录 B，由 data/*.csv 生成）

表名通用，**字段按品类替换**：

1 时间轴与结构配比｜2 单位/敌人数值表（有效血量 · 输出 · 行为模式）｜3 成长曲线 vs 压力曲线（配图）｜4 资源产出、换算与定价｜5 难度修饰表｜6 内容池结构（稀有度×数量×权重×覆盖率）｜7 经济收支（来源×去向）｜8 路径期望（集齐一套构筑/养成/毕业的期望）｜9 单次行动收益表（费效比 / DPS / 每次操作的产出）｜10 行为时序与信息表（敌人 AI / 对手模式 / 关卡节奏）

**合格标准**：把表里两列一除，能算出你判断里那个数。

**凡是"攒齐 / 成型 / 毕业 / 通关率"类结论，都必须算期望，不许只写体感。** 例（卡牌游戏）：一局 N 次奖励、每次 3 选 1、三件套在池中 a+b+c 张、池总 M 张 → 命中率 p≈(a+b+c)/M，集齐期望 ≈ 1.83/p；期望 > N 就说明"自然成型"是小概率事件。其他品类换池子与抽取次数，算法同理。**分母写清楚**（见「写算式先问三个问题」）。

## 产物落在哪：两种模式（第 0 步先判）

开拆前先看当前目录，二选一，**拿不准就问一句，不要默认**：

| | 触发条件 | 交付物 | 建什么 | 收尾 |
|---|---|---|---|---|
| **索引仓库模式** | 当前目录是一个索引仓库：根目录有封面 `README.md`（索引表里列着别的游戏），或已有别的 `<游戏>/` 文件夹 | `<游戏-slug>/拆解案.md` | `<游戏-slug>/` 下的 `拆解案.md` / `images/` / `data/` / `shots/` / `tools/`。**不建 `.gitignore`**——根目录那份的 `shots/` 与 `.teardown-progress.md` 两条规则不带斜杠前缀，天然覆盖子目录 | 在封面 `README.md` 的索引表里加一行（游戏 · 品类 · 版本锚点 · 链接到拆解案） |
| **独立仓库模式** | 空目录，或目录里没有索引特征 | `README.md` | `README.md` / `images/` / `data/` / `shots/` / `tools/` / `.gitignore` / `.teardown-progress.md` | 无需改别的文件 |

`<游戏-slug>` 用英文小写连字符，例如 `slay-the-spire-2`。**除落地路径外，两种模式下面所有内容完全一样。**

## 流程

**第 0 步 · 判模式 + 定形状 + 建目录 + 逼观点。** 判落地模式 → 定交付物形状（六域拆解 / 旅程复盘 / 机制对照）
→ 问清拆哪个游戏、**属于哪个品类**（认领上面那一行）、用户最想说的 3-5 条 → 建目录。
过一遍六个域，标注哪些硬性待填、哪些可折叠。**形状若中途变更，回这一步重判，并写明理由。**

**第 1 步 · 设计数据采集（动笔前做）。** 把用户已说的感受逐条过翻译表 → 得到该问的设计问题与该记的字段 → 布置 1-3 条观察任务，写进进度文件台账。

**第 2..N 步 · 逐域深挖。** 一次一个域，先落事实再写拆解与判断，落笔即追加进拆解案文档。**绝不整篇重写。** 续接时只读 `.teardown-progress.md`，不重读正文。

**收尾 · 六步，顺序不可换。** ① 落完正文 → ② 过一遍脚本能查的自检项 → ③ **跑一轮证伪**（见「收尾前跑一轮证伪」）
→ ④ 按证伪结论改写正文 → ⑤ 过判断项与校验项 → ⑥ 更新进度文件。

## 感受 → 设计问题（本 skill 的核心动作）

| 用户说 | 该问 | 该记 |
|---|---|---|
| 卡在这关了 / 打不过 | 该关或该敌人的数值 vs 玩家在该节点的期望输出（三）；它是必经还是可选（二） | 名称、战前战后状态、耗时或回合数 |
| 前期太劝退 | 开局配置的能力 vs 前期压力（三）；前期的结构配比与引导（二/六） | 前 30 分钟的失败次数与卡点位置 |
| 太简单 / 后期无聊 | 后期还剩多少决策密度、成型后还有没有改变打法的选择（一/五）；战力是否碾压压力曲线（三） | **单位时间内的有效决策次数**（数出来）、输出 vs 压力 |
| 变强 / 成型很爽 | 成型前后战力差几倍（三）；集齐一套在池中的期望（四） | 成型时点、成型前后单次行动的产出 |
| 这局运气不好 | 随机作用在哪几层、有无权重与保底（四） | 随机事件的类型与出现频次 |
| 不知道该干什么 | 目标与引导的信息层级（六）；结构配比是否给足提示（二） | 卡住那一刻的界面状态 |
| 一直在攒资源 / 不够用 | 产出与消耗速率、定价（三/四） | 单位时间的资源收支 |
| 重复感强 | 内容池多大、变体多少（四/二） | 重复出现的关卡 / 敌人 / 事件**各几次** |
| 某某系统没存在感 | 该系统的收益是否被更强的系统盖过（四/三） | 该系统单位时间的产出占比 |
| 手感怪 / 反馈不清 | 反馈层级与信息层级（六） | 关键操作的反馈清单 + 截图 |
| 玩不动了 / 不想上号 | 留下来的是习惯、等待还是**沉没成本**？（四）它每天要续期吗？ | 触发事件、驱动力出自哪套系统、有无前瞻性预测 |

找不到行就现场造一行。**感受是入口，不是结论。**

## 数据从哪来

正文每条数值逐项标注来源。**媒体文章的数字一律不采用**——媒体不校数值，被追问一句就崩；媒体只能支撑观点。

| 档 | 负责 | 标注 |
|---|---|---|
| **实测** | 单位数值、损耗、节点计数、关键决策、成长时点、价格 | 标**样本量 n** |
| **自陈** | 观察者即被观察者——自我民族志、回溯自述 | 标 **n=1**，并写明**回溯偏差**（距事件多久） |
| **公开** | 内容池权重、掉落与概率规则、难度修饰表、官方数值 | 给**链接与版本**；必须来自 wiki / 数据库 / 官方 |
| **推断** | 期望、概率、比值、折算 | 给**算式**，并落成**可复算的脚本** |

- 客观数值（血量 / 价格 / 伤害 / 帧数）1 次记录即可；统计规律（频率 / 胜率）要 n≥20；节奏与时长类要 5 局起步。**混着写却不给 n 是可信度事故。**
- 每条推断写明**哪些结论建立在它之上**。
- **自陈是个特殊档**：它和实测同形，可信度不同。引用自陈项时，正文必须能看出"这是自述"还是"这是行为证据"——混为一谈就是把回忆当成记录。

## 硬规则

1. 术语首次出现中英对照，按品类取：核心循环（core loop）、元进度（meta progression）、构筑（build）、难度曲线（difficulty curve）、有效生命（EHP）、击杀耗时（TTK）、资源产出与消耗（faucet / sink）、保底（pity）。
2. 判断必须带**内部基准 + 外部对标**（同品类作品），对标落到一个具体取舍点上，不是"跟某某比如何"。
3. **区分设计意图与实际体验**——两者不一致时明说，这本身就是好观点。
4. 禁用词：众所周知、可以看出、非常出色、体验极佳、设计得很棒。拆解案特有的空转词：系统丰富、互相配合、平衡做得不错、增加了重玩性、策略性强——这几个后面**必须接一个数或一条规则**。
5. **用定性构念就得给数。** "决策密度 / 信息透明度 / 强度落差 / 重复感"这类词，同段必须配一个可核对的计数（次数 / 秒数 / 关卡数 / 局数）。写了"决策密度为 0"而没数过一次 ＝ 违规。
6. 篇幅：正文 6000-9000 字，**单个硬性单元 ≤1200 字**（六域拆解里是一个域，旅程复盘里是一个节点），图 8-15 张，每个硬性域 ≥1 张表或图。超了砍重复的参照物与无观点描述，**不许砍事实段与算式**。
7. 截图走文件系统、不进对话：原始图丢 `shots/`，成品放 `images/`（`01-xxx.png` 编号），对话里只出现文件名与图注。图注写"这张图说明了什么"，不是"游戏截图"。
8. `data/` 要发布（CSV 会被 GitHub 渲染成表格，附录 B 的表由它生成）；`tools/` 放复算脚本；`.teardown-progress.md` 与 `shots/` 进 `.gitignore`。

## 拦停

- **事实层**：数值当场拿不到 → 转观察任务；任务也做不了 → 标"（估算）"或降级为推断并给算式。**不许含糊过去。**
- **判断层**：追问三轮仍说不清 → 这段不写，记进「待补的判断」，并给出具体观察任务：
  ❌"再体验一下后期" ✅"接下来 5 局，每场 Boss 或强敌战后记名称、战前战后状态、耗时"。
- **整个交付物层**：材料薄到撑不起所选形状的硬性单元 → 不硬凑、不静默缩水，回第 0 步改形状，并写明理由。

## 怎么保证拆得对

六域是骨架，但骨架立不起来不等于结论对。收尾时做三件事。

**写算式，先问三个问题。** 凡是概率、期望、"攒齐 / 毕业 / 覆盖率 / 达成率"类结论，必须写成算式。但算式合格有三问：

1. **分子是什么？分母是什么？** 写出来，不许只在文字里带过。
2. **这个分母是我真正想度量的那件事吗？** 换一个合理的候选分母，**结论会不会翻盘**？会翻盘 → 分母是选出来的，不是算出来的，必须换掉或降级。
3. **能不能被复算？** 落成脚本。

> 反例（真实发生过）：把"回归礼包的追赶量 ÷ 离线期间错过的总产出"当作"礼包够不够留住人"的度量，
> 算出 0.32%。算式干净、来源齐全、自检全过——**但分母错了**：留住人的门槛不是"补齐缺口"，
> 是"够得着当期门槛"。**分母选错的量化结论比没有结论更危险，因为它带着一层算术的权威。**

**收尾前跑一轮证伪。** 落完正文之后、过自检之前，扮演这份文档最强的对手：

1. 用一句话反驳每一处判断。**反驳成立的就加固、降级或删掉。**
2. 列出最容易被一句话击穿的三处，逐条处置。
3. 专查四类病：分母换个候选会不会翻盘；**相关有没有被写成因果**；有没有数没被数过却当事实用；**自陈有没有被当作实测**。
4. **判负要留痕**：改写或降级的判断，在正文对应处写明"此处曾判负，已改写"，并记进进度的「证伪记录」。

**推断要能被复算。** 附录里的每条推断，都要有一份能一键重跑的脚本（惯例 `tools/make-data.py`），
产出正文引用的全部数值与 `data/*.csv`。**合格标准：换个人拿到仓库，只跑脚本就能复现正文里每一个数。**
脚本只做算术，不引入正文没有的新数值；每个常数注明来源档位。

- [ ] **分母复算**：抽一条量化结论，写出它的分子与分母，**换一个合理的候选分母重算，看是否翻盘**。翻盘 → 回炉。
- [ ] **基准复算**：抽一条判断的「内部基准」，独立重算一遍，看是否支持该判断。
- [ ] **因果检查**：抽一条含"因为…所以…"的判断，检查证据是否只支持相关。只支持相关 → 改成相关表述或降级。
- [ ] **证伪轮已跑**：进度文件里有本轮证伪记录，判负的改动在正文留了痕。
