# 游戏拆解案

把一个游戏拆成一份**经得起追问的专业拆解案**。**适用于任何品类**——动作、射击、RPG、开放世界、关卡制、卡牌、策略、模拟经营、竞技、解谜、免费手游。产物是一份 markdown 文本，落在哪分两种模式（见「产物落在哪」）：独立仓库里它就是 `README.md`（GitHub 首页直接渲染），索引仓库里它就是 `<游戏>/拆解案.md`。**本 skill 不碰 git**，上传是用户的事。

## 三条地基

1. **框架是骨。** 正文按六个设计域组织，不按用户的印象组织。框架规定要拆什么。
2. **内容从追问来。** 用户手里有游戏——数值、系统规则、关卡结构只有他能提供。访谈负责把"那关打不过"翻译成"该关敌人的有效血量 vs 玩家在该节点的期望输出"。
3. **事实是地板，判断是天花板。** 「用户没有观点」只豁免判断段，**不豁免事实段**。硬性域的事实段为空 = 没拆完。

## 六个域（通用）

| 域 | 必答 | 必产 |
|---|---|---|
| 一 · 核心循环与节奏 | 三层循环（单次操作 / 单局或单段 / 长线）、重心在哪层、时间轴、多久一次**有意义的决策**（不是操作） | 表 1 + 循环图 |
| 二 · 内容结构与关卡 | 关卡/地图/模式/阶段的划分与配比、硬门槛与保底、路径分支与**绕行成本**、崩盘点落在哪 | 表 1 + 结构图 |
| 三 · 数值与经济 | 结算结构（加算/乘算）、单位数值、成长曲线与压力曲线、两者比值、资源产出与定价、难度修饰、阈值与溢出 | 表 2-5 |
| 四 · 系统与内容池 | 逐系统走：目标→规则→输入输出→反馈→失败惩罚→边界漏洞。内容池（掉落池/技能池/关卡池…）、解锁与元进度、商业化（若适用） | 表 6-8 |
| 五 · 玩法机制 | 核心机制的经济：单次行动的收益与成本、可操作空间、信息透明度、上限与代价 | 表 9-10 |
| 六 · 反馈与表现（可选） | 一次交互的反馈层级、信息层级、手感与可读性、教学与引导 | 截图 |

**只有域六**允许"用户无观点就整域折叠"。其余五个域不豁免。

## 先定品类，再拆

同一套域，在不同品类里的内容不同。开拆前先认领一行，域二与域五照它替换：

| 品类 | 域二看什么 | 数值单位 | 内容池 | 机制经济（域五） |
|---|---|---|---|---|
| 动作 / 射击 | 关卡节奏、遭遇战布局、检查点 | DPS、TTK、命中与暴击期望 | 武器 / 技能池 | 单次交火的输出与生存成本 |
| 平台 / 关卡制 | 关卡与教学曲线、难度坡 | 移动速度、容错窗口 | 关卡池、机制池 | 操作精度与容错帧 |
| RPG / 开放世界 | 区域与任务结构、引导与自由度 | 属性、等级曲线、装备强度 | 装备 / 任务 / 敌人池 | 资源回路（血/蓝/药/金币） |
| 卡牌 / 回合制 roguelike | 层与节点配比、路线成本 | 有效血量、每回合输出 | 卡池、事件池 | 能量与费效比 |
| 策略 / 模拟经营 | 关卡或剧本结构、阶段目标 | 产出与消耗速率、平衡比 | 单位 / 科技 / 建筑池 | 决策的收益与延迟 |
| 竞技 / 多人 | 地图与模式结构、匹配机制 | 平衡数值、胜率 | 英雄 / 装备池 | 信息与反应窗口 |
| 解谜 / 休闲 | 关卡与难度序列 | 步数 / 时间 / 容错 | 关卡池、机制池 | 信息充分性 |
| 免费手游 | 引导与留存节点、卡点设计 | 体力与钻石的产出/消耗 | 卡池与概率 | 付费与玩法的挂钩 |

（示例字段，不是清单；不适用的格子跳过。）

## 每个域写三段

- **事实** — 数值表 / 规则 / 配比，一条一行，逐项标来源。**空着就是没拆。**
- **拆解** — 现象 → 机制 → 设计意图 → 代价与收益。机制必须落到数值或规则上：❌"那关太难" ✅"该关敌人有效血量 X、玩家期望输出 Y、需要 N 回合（或 N 秒），超过这个数就没有容错空间"。
- **判断** — 一句可被反驳的话 + 内部基准 + 外部对标 + 边界。想不清就写「本域无判断，待观察 X」。

**防退回说明书**：每域必须以判断收尾；空域显式留白，禁为凑齐而灌水。

## 文档骨架

产品卡片（平台/品类/上线/体量/样本量）· 核心发现索引（3-5 条跨域判断，**每条注明出自哪个域**）→ 域一…域六 → 它付出的代价 → 如果我来迭代 → 附录 A 系统依赖（mermaid）· B 数值细节与交付物表 · C 曲线与图 · D 数据来源与可信度（实测/公开/推断三节 + 推断表）· E 术语表。附录全部 `<details>` 折叠，结论前置。

## 交付物表（附录 B，由 data/*.csv 生成）

表名通用，**字段按品类替换**：

1 时间轴与结构配比｜2 单位/敌人数值表（有效血量 · 输出 · 行为模式）｜3 成长曲线 vs 压力曲线（配图）｜4 资源产出、换算与定价｜5 难度修饰表｜6 内容池结构（稀有度×数量×权重×覆盖率）｜7 经济收支（来源×去向）｜8 路径期望（集齐一套构筑/养成/毕业的期望）｜9 单次行动收益表（费效比 / DPS / 每次操作的产出）｜10 行为时序与信息表（敌人 AI / 对手模式 / 关卡节奏）

**合格标准**：把表里两列一除，能算出你判断里那个数。

**凡是"攒齐 / 成型 / 毕业 / 通关率"类结论，都必须算期望，不许只写体感。** 例（卡牌游戏）：一局 N 次奖励、每次 3 选 1、三件套在池中 a+b+c 张、池总 M 张 → 命中率 p≈(a+b+c)/M，集齐期望 ≈ 1.83/p；期望 > N 就说明"自然成型"是小概率事件。其他品类换池子与抽取次数，算法同理。

## 产物落在哪：两种模式（第 0 步先判）

开拆前先看当前目录，二选一，**拿不准就问一句，不要默认**：

| | 触发条件 | 交付物 | 建什么 | 收尾 |
|---|---|---|---|---|
| **索引仓库模式** | 当前目录是一个索引仓库：根目录有封面 `README.md`（索引表里列着别的游戏），或已有别的 `<游戏>/` 文件夹 | `<游戏-slug>/拆解案.md` | `<游戏-slug>/` 下的 `拆解案.md` / `images/` / `data/` / `shots/`。**不建 `.gitignore`**——根目录那份的 `shots/` 与 `.teardown-progress.md` 两条规则不带斜杠前缀，天然覆盖子目录 | 在封面 `README.md` 的索引表里加一行（游戏 · 品类 · 版本锚点 · 链接到拆解案） |
| **独立仓库模式** | 空目录，或目录里没有索引特征 | `README.md` | `README.md` / `images/` / `data/` / `shots/` / `.gitignore` / `.teardown-progress.md` | 无需改别的文件 |

`<游戏-slug>` 用英文小写连字符，例如 `slay-the-spire-2`。

**除了落地路径，下面所有内容两个模式完全一样**——六个域、每域三段、交付物表、硬规则、拦停、自检，一条不改。

## 流程

**第 0 步 · 判模式 + 建目录 + 定品类 + 逼观点。** 先按「产物落在哪」判模式，再问清拆哪个游戏、**属于哪个品类**（认领上面那一行）、用户最想说的 3-5 条。建目录：独立仓库模式建 `README.md` / `images/` / `data/`（要发布）/ `shots/`（不进产物）/ `.gitignore` / `.teardown-progress.md`；索引仓库模式建 `<游戏-slug>/拆解案.md` + `<游戏-slug>/images/` + `<游戏-slug>/data/` + `<游戏-slug>/shots/`。过一遍六域，标注哪些硬性待填、哪些可折叠。

**第 1 步 · 设计数据采集（动笔前做）。** 把用户已说的感受逐条过翻译表 → 得到该问的设计问题与该记的字段 → 布置 1-3 条观察任务，写进进度文件台账。

**第 2..N 步 · 逐域深挖。** 一次一个域，先落事实再写拆解与判断，落笔即追加进拆解案文档（索引仓库模式是 `拆解案.md`，独立仓库模式是 `README.md`）。**绝不整篇重写。** 续接时只读 `.teardown-progress.md`，不重读正文。

**收尾 · 自检。** 过文末清单。

## 感受 → 设计问题（本 skill 的核心动作）

| 用户说 | 该问 | 该记 |
|---|---|---|
| 卡在这关了 / 打不过 | 该关或该敌人的数值 vs 玩家在该节点的期望输出（三）；它是必经还是可选（二） | 名称、战前战后状态、耗时或回合数 |
| 前期太劝退 | 开局配置的能力 vs 前期压力（三）；前期的结构配比与引导（二/六） | 前 30 分钟的失败次数与卡点位置 |
| 太简单 / 后期无聊 | 后期还剩多少决策密度、成型后还有没有改变打法的选择（一/五）；战力是否碾压压力曲线（三） | 单位时间内的有效决策次数、输出 vs 压力 |
| 变强 / 成型很爽 | 成型前后战力差几倍（三）；集齐一套在池中的期望（四） | 成型时点、成型前后单次行动的产出 |
| 这局运气不好 | 随机作用在哪几层、有无权重与保底（四） | 随机事件的类型与出现频次 |
| 不知道该干什么 | 目标与引导的信息层级（六）；结构配比是否给足提示（二） | 卡住那一刻的界面状态 |
| 一直在攒资源 / 不够用 | 产出与消耗速率、定价（三/四） | 单位时间的资源收支 |
| 重复感强 | 内容池多大、变体多少（四/二） | 重复出现的关卡 / 敌人 / 事件 |
| 某某系统没存在感 | 该系统的收益是否被更强的系统盖过（四/三） | 该系统单位时间的产出占比 |
| 手感怪 / 反馈不清 | 反馈层级与信息层级（六） | 关键操作的反馈清单 + 截图 |

找不到行就现场造一行。**感受是入口，不是结论。**

## 数据从哪来（双轨）

| 轨道 | 负责 | 标注 |
|---|---|---|
| 玩家记录 | 单位数值、损耗、结构与节点计数、关键决策、成长时点、价格 | 实测，**给样本量 n** |
| 公开查证 | 内容池权重、掉落与概率规则、难度修饰表、官方数值 | 公开，**给链接**。数值必须来自 wiki / 数据库 / 官方 |
| 推导 | 期望、概率、比值 | 推断，**必须给算式** |

- **媒体文章的数值不能用**——媒体不校数值，被追问一句就崩。媒体只能支撑观点。
- 客观数值（血量/价格/伤害/帧数）1 次记录即可；统计规律（频率/胜率）要 n≥20；节奏与时长类要 5 局起步。混着写却不给 n 是可信度事故。
- 每条推断进附录 D，并写明哪些结论建立在它之上。
- **观察任务** = 明确时机 + 可勾选字段 + 样本量，一次最多 3 条，写进台账；两轮没动静就拆小或取消。

## 硬规则

1. 术语首次出现中英对照，按品类取：核心循环（core loop）、元进度（meta progression）、构筑（build）、难度曲线（difficulty curve）、有效生命（EHP）、击杀耗时（TTK）、资源产出与消耗（faucet / sink）、保底（pity）。
2. 判断必须带**内部基准 + 外部对标**（同品类作品），对标落到一个具体取舍点上，不是"跟某某比如何"。
3. **区分设计意图与实际体验**——两者不一致时明说，这本身就是好观点。
4. 禁用词：众所周知、可以看出、非常出色、体验极佳、设计得很棒。拆解案特有的空转词：系统丰富、互相配合、平衡做得不错、增加了重玩性、策略性强——这几个后面**必须接一个数或一条规则**。
5. 篇幅：正文 6000-9000 字，**单域 ≤1200 字**，图 8-15 张，每个硬性域 ≥1 张表或图。超了砍重复的参照物与无观点描述，**不许砍事实段与算式**。
6. 截图走文件系统、不进对话：原始图丢 `shots/`，成品放 `images/`（`01-xxx.png` 编号），对话里只出现文件名与图注。图注写"这张图说明了什么"，不是"游戏截图"。
7. `data/` 要发布（CSV 会被 GitHub 渲染成表格，附录 B 的表由它生成）；`.teardown-progress.md` 与 `shots/` 进 `.gitignore`。

## 拦停

- **事实层**：数值当场拿不到 → 转观察任务；任务也做不了 → 标"（估算）"或降级为推断并给算式。**不许含糊过去。**
- **判断层**：追问三轮仍说不清 → 这段不写，记进「待补的判断」，并给出具体观察任务：❌"再体验一下后期" ✅"接下来 5 局，每场 Boss 或强敌战后记名称、战前战后状态、耗时"。

## 进度文件 `.teardown-progress.md`（永不发布）

已确立的判断 / **域覆盖状态**（六域 × 事实·拆解·判断）/ **交付物清单状态** / **数据采集台账**（任务·字段·样本量·状态·回来了填进哪张表）/ 待验证 / 待补的判断 / 待查的公开数据 / 截图清单 / 会话日志。

每次落笔后更新；每次会话收尾布置 1-3 条观察任务，并报一句"下次带什么数据回来、从哪继续"。

## 自检（缺一条不算完成）

- [ ] 落地模式判对了：索引仓库模式 → 交付物是 `<游戏-slug>/拆解案.md`，且封面索引表已加行；独立仓库模式 → 交付物是 `README.md`
- [ ] 品类已认领，域二与域五按该品类的口径写
- [ ] 五个硬性域的**事实段**都非空
- [ ] 每个硬性域有判断收尾，或显式写「本域无判断 + 待观察 X」
- [ ] 至少一条结论写成了算式（涉及概率、期望、"攒齐""毕业"的必须写）
- [ ] 所有数值标了来源；没有一条数值引用来自媒体文章
- [ ] 前置的「核心发现」有 3-5 条跨域判断，每条注明出自哪个域
- [ ] 「如果我来迭代」有真的立场，每条带代价，且落得到具体数值或规则
- [ ] 全文无禁用词，术语首次出现有中英对照
- [ ] 没有把"待补"忘在正文里——要么补上，要么写明打算回去验证什么
- [ ] 进度文件已更新（域状态 / 数据台账 / 待验证）
